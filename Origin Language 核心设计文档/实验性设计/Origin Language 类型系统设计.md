# Origin Language 类型系统设计

> 定位：类型系统是 Origin 的**环境层规则**，不是核心的一部分。本文档确立其设计原则与结构骨架，并在后续章节逐步细化具体规则。

## 定位（一句话）

> **类型标注属于结构，类型检查属于环境。** 强弱类型不是两套语言，而是同一套结构在环境不同解释策略下的表现；模式由决策者在**源代码一侧**显式声明（因结构不变性，一开始就定），编译期与运行期环境读取该声明并选择对应的解释策略。

## 设计原则

### P1 结构与解释分离

类型标注（类型语法、类型符号、类型关系描述）属于**结构**；类型检查（是否检查、何时拒绝、如何推导）属于**环境的解释规则**。两者正交。

- 理由：Origin 核心「结构保持，环境响应」的直接推论。源代码只描述关系，不携带执行规则；检查是环境对结构的响应。

### P2 核心中立

Origin 核心不内置任何类型规则，不持有强/弱类型的任何立场。强弱类型的选择、类型规则的实现，全部由环境承担（编译期环境或运行期环境）。

- 理由：类型是「想要的功能」而非「存在事实」。核心只保留无法省去的最小抽象（Unknown 锚点 + compiler 应用接口），不越权替环境做类型决定。

### P3 策略声明在源代码一侧

强弱类型的选择由决策者在**源代码中**显式声明（位于源代码开头）。因结构不变性，模式声明一旦写入即固定，属于结构的一部分；环境（编译期/运行期）读取该声明并选择对应的解释策略。禁止环境在源代码未声明时自行猜测。声明分两级（工程级与区域级），见后文「模式声明的两级形式」。

- 理由：结构保持，环境响应——模式声明是结构，选择策略是环境对该结构的响应。显式优于隐式。

### P4 默认弱类型

源代码未声明模式时，环境按**弱类型模式**解释。

- 理由：兼容方向决定默认。弱类型可以兼容强类型（强类型模式通过的结构，在弱类型模式下行为一致，见 P6），而强类型无法兼容弱类型（弱类型形式的结构在强类型模式下会被拒绝）。默认取兼容性更大的一侧，保证任何源代码都能运行；想要严格检查的决策者显式声明强类型模式即可。

### P5 同构不同释

强类型与弱类型**不是两套类型系统**，而是同一套结构（含类型标注）在两种检查策略下的解释。策略差异只体现在「是否介入检查、何时拒绝」，不体现在结构形式上。

- 理由：避免出现两套并行语言；结构保持单一，才能保证「结构不变，环境响应」成立。

### P6 兼容单调

类型检查策略构成有序关系：**强类型策略是弱类型策略的加严**（弱 ⊃ 强）。强类型策略下通过的结构，在弱类型策略下必须同样通过，且行为一致；强类型策略多出的约束只有——类型被强制检查、缺类型且不可推导即拒绝（见后文「类型强制策略」）。

- 理由：保证策略切换不产生意外行为；强类型模式是弱类型模式的子集语义，切换只增加约束、不改变既有含义。P4 的默认选择正是由此推出。

### P7 编译期与运行期各司其职，共同服从源代码声明

编译期环境与运行期环境都读取源代码的模式声明；检查职责的划分（静态检查 vs 动态检查）属于各自环境，但两边的解释策略都服从同一份源代码声明，不得互相矛盾。

- 理由：编译与运行本来就是两层环境；模式由源代码声明统一定调，职责由正在解释该结构的环境就近划分。

### P8 确定性

同一结构、同一策略配置下，重复解释结果一致。

- 理由：沿用《实现者指南》的确定性要求。策略是解释规则的一部分，解释必须可预期、可回溯。

### P9 可回溯诊断

策略拒绝发生时，诊断必须定位到具体结构与具体判定；不允许静默失败。

- 理由：诊断是环境的责任。检查策略的每一处拒绝都应可被决策者预判和定位。

### P10 类型不引入新类别

类型符号本身是值（可区分、可参与组合）；类型系统不引入独立于「值」的新类别。每个新概念加入前必须回答：它落在四元本体论的哪一元？它是「必需的」还是「想要的功能」？

- 理由：与核心的四元本体论（值 · 操作 · 环境 · 组合）保持一致；想要的功能移出核心，交给环境生长。

### P11 模式穿透受显式控制

强类型模式环境**可以**决定是否允许弱类型的表达方式**穿透**进入（即强类型代码中使用弱类型的表达）。若允许，必须满足两个条件：① 源代码中用显式标记声明穿透区域（可审计）；② 穿透区域的结果回到强类型模式时，必须经过显式的**边界转换**与运行时检查——否则强类型模式的保证会静默泄漏。反向无需穿透：强类型形式的表达在弱类型模式中直接按弱类型策略解释即可。

- 理由：穿透由正在解释这个结构的环境决定（《Origin Language 核心抽象设计》「穿透」一节）。强 ⊂ 弱只说明「强类型形式代码在弱类型模式下成立」，不说明「弱类型形式表达可以在强类型模式下免检」；允许穿透是环境的决定，但边界必须显式，否则违反 P6 与 P9。

### P12 检查策略的双重视角

检查策略在**结构视角（源代码一侧）是值**，可被操作；在**环境视角（运行时一侧）是环境**，不可被操作。

- 源代码一侧：类型系统环境提供两种策略（强类型策略 / 弱类型策略）作为可选值，决策者通过源代码开头的模式声明（P3）选择其一并告知环境——模式声明即「引用策略值」的结构。策略作为值时，可被结构引用、传递、参与组合。
- 运行时一侧：被选中的策略成为解释当前源代码的环境（既定条件），不可被正在被解释的程序操作——不存在「运行时切换检查策略」。
- 两个视角互斥发生，不存在递归依赖（《Origin Language 核心抽象设计》「环境」一章）：运行时不可能操作「正在解释自己的环境」；源代码侧操作的只是尚未成为环境的策略值。
- 具体元操作（查询、传递、构造新策略等）的形式留在后续章节展开；其中「构造新策略」属于「源代码构造环境」的能力，并在后续章节继续细化。

- 理由：与「值、操作、环境是不同观察层次下对现实结构的不同抽象」一致；同时保证 P8 确定性——运行时策略不可变，同一配置下解释一致。

## 弱类型模式的语义骨架

> 说明：弱类型模式是默认模式（P4），其语义依赖穿透边界转换与 P6 兼容单调；本节给出语义骨架，并在后续章节扩展细节。

### 1. 「弱」的定性：不检查、不转换、操作自行解释

弱类型模式的「弱」是**类型系统层面的不介入**：

1. **不检查**：环境不因类型关系拒绝任何结构。值可以进入任何操作数位置；「类型拒绝」在弱类型模式下不是可判定的状态。不为此引入 Any 之类的特殊类型概念（P10）。
2. **不转换**：类型系统不提供全局隐式转换机制。隐式转换会让类型系统在「不介入」的同时又介入，概念自相矛盾，且静默改变值、与 P9 可回溯诊断冲突。
3. **操作自行解释**：原子操作对参数的解释规则由操作自身定义（操作由环境提供并解释）。若某个操作需要宽容行为，那是该操作的解释规则，不是类型系统的机制。

- 放弃「全局隐式转换」（自动适配式弱类型）。理由：它把类型系统职责混入操作职责；保留操作级宽容，但归属操作自身。

### 2. 操作解释规则模式无关

同一原子操作在强/弱类型模式下的解释规则**相同**；强/弱类型模式的差异只在于类型系统的检查是否介入（强类型模式检查、弱类型模式不检查），不改变任何操作本身的解释。

- 理由：这是 P6 兼容单调在操作层的保证——否则「强类型模式通过的结构在弱类型模式下行为一致」会被操作层破坏。

### 3. 类型位置在弱类型模式下的地位：不响应

- 类型属于结构（P1）。弱类型模式环境对类型**不响应**：类型不参与检查、不产生诊断、不影响解释结果。
- 弱类型源代码可以写类型也可以不写；写了也只作为结构存在，环境选择不看。
- 「部分使用类型」（如作提示用于诊断或优化）属于环境的可选增强，不在当前骨架内，后续可据需扩展。

### 4. 失败语义：落回 Unknown 锚点

- 弱类型模式不拒绝结构，因此不存在「类型拒绝」。类型系统层面的失败只有一种：**操作名未绑定**（名称查找失败，《语义设计》「操作失败的统一响应」）。
- 此时结果落回核心公共锚点：以 Unknown 承载（载荷为名称与参数等，形态由环境决定），并可继续传递、暂存或作为边界返回值。
- Unknown 不是诊断：弱类型模式下不产生类型诊断。Unknown 携带的名称与参数提供可回溯性，与 P9 不冲突（P9 约束的是「拒绝与转换」，弱类型模式两者皆无）。
- 「运行期类型检查」若存在，只出现在强类型模式的穿透边界；弱类型模式内部没有。

### 5. 共享结构层：类型位置语法唯一

- 类型只有**一套写法**（声明结构中的类型位置，《语言结构设计》「绑定」/「操作构造：lambda」/「类型声明」），强/弱类型模式共享；不因模式而有两种类型写法。
- 同一份带类型的源代码：强类型模式下类型被强制检查（响应），弱类型模式下类型被忽略（不响应）。
- 推论：模式声明（P3）是源代码开头的一种特殊结构，与类型位置同属「结构层唯一」的一部分。

### 6. 骨架边界（不在当前骨架内，后续扩展）

- 各原子操作的具体解释表——属于操作自身，不在此定义。
- 强类型模式的具体检查——见后文「强类型模式的语义骨架」。
- 诊断格式、运行期检查机制、类型「部分使用」的可选增强——后续生长。

## 强类型模式的语义骨架

> 说明：弱类型模式是默认模式（P4），强类型模式是显式声明的加严模式（P6）。本节给出强类型模式的语义骨架，与前文「弱类型模式的语义骨架」对称；类型宇宙与类型写法在后续章节扩展。

### 1. 「强」的定性：判定，不转换

强类型模式的「强」是**类型系统介入检查**：

1. **判定**：环境响应结构中的类型，判定类型关系；关系不成立 → 拒绝。
2. **不转换**：类型系统只判定，不做隐式转换——一切转换必须显式书写。与弱类型模式（见前文「弱」的定性）一致：类型系统在两种模式下都不改变值；差别只在「是否介入判定」。
3. **判定与转换分离**：类型关系判定不伴随任何隐式转换；操作解释规则模式无关（见前文「操作解释规则模式无关」）在此体现——检查不改变操作、不改变值。

### 2. 检查对象

强类型模式判定三类类型关系：

1. **可绑定位置**（操作参数 / 返回 / 字段 / 名称绑定）具有显式写的类型或可推导的类型；
2. **操作调用**：每次调用中，操作数的类型与操作声明的参数类型关系成立；
3. **穿透边界**：弱类型区域的结果回归强类型模式时，边界转换成立（见后文「区域级声明」）。

判定结果三态：**成立 / 不成立 / 未知**。「未知」（缺类型且不可推导）一律按拒绝处理，不允许静默放行。

### 3. 类型强制策略：显式为主 + 受限局部推导

- **边界显式**：参数、返回、字段、绑定到环境的名称——必须显式写类型（它们是接口契约，不可推导）；**lambda 特例**：绑定 lambda 时不另写类型——lambda 自带参数类型、返回类型由体的 return 决定（《语言结构设计》「操作构造：lambda」），类型来自 lambda 自身而非推导；
- **局部推导**：仅在初始化的值结构的局部位置，允许由值推导类型；推导失败或超出局部范围 → 诊断。
- 缺类型且不可推导 = 拒绝（诊断）——这是「强」的严格性来源。

### 4. 拒绝与诊断（与 Unknown 严格区分）

- 强类型模式的拒绝触发**诊断**（诊断是操作，结果为诊断值）。诊断同样落在四元本体论内：
  - **源代码侧**：诊断是**组合**——源代码中描述「在何处、以何种条件触发诊断」的关系结构；
  - **运行时侧**：诊断是**操作**——真实发生作用（产生诊断值并反馈给决策者）；
  - **诊断值**：是**值**——可区分、可传递，可被结构中的更高层操作捕获或处理（与《实现者指南》「关于错误和边界情况」一致：诊断值是环境返回的特殊值，纳入组合关系而非排除在外）。
- 与弱类型模式对照：弱 = 操作名未绑定 → Unknown 值继续传递；强 = 类型关系不成立 → 产生诊断（操作发生作用，结果为诊断值）。诊断的影响范围**收窄到最近的环境**：正在判定该结构的（最近）环境**终止对该结构的本次解释**；诊断值沿组合层级向上传递，可被更高层操作捕获或到达决策者；**结构本身仍是值**，不因此失效，可交由其他环境继续解释。
- 与 Unknown 的区分：两者同为值、同可传递，但语义不同——Unknown 是核心锚点承载「未解释」的结构；**反馈给决策者的是诊断值**，它承载环境「已判定并拒绝」的结论。诊断（操作）本身不是反馈，反馈的是它的作用产物（诊断值）。
- 时机分工（P7）：静态可判定 → 编译期诊断；动态判定（穿透边界）→ 运行期诊断。
- 诊断可回溯（P9）：定位到具体结构与具体规则。

### 5. 骨架边界（不在当前骨架内，后续扩展）

- **类型宇宙**：基础类型、复合类型、类型关系的具体种类与判定——逐项生长。
- **推导算法**、**诊断格式**——留后续章节。
- 数值加宽已决策（见后文「类型关系判定的机制」）：不设隐式关系，int → long 等加宽必须显式转换。

## 模式声明的两级形式

> 这里把声明形式与穿透标记统一为同一机制的两级：工程级（B 式）与区域级（A 式）。

### 1. 工程级声明（入口文件，一次声明全局生效）

- 声明位置：**入口文件**——整个工程源代码集合的入口。声明一次，作为整个工程的解释策略；其余文件不重复声明（该声明对整个工程生效）。
- 机制：入口声明是「源代码构造环境」的操作（《Origin Language 核心抽象设计》「源代码」一章）——决策者为工程环境选择策略。策略一旦生效即成为该环境的既定规则，按 P12 运行时侧不可再变（工程运行中不可切换）。
- 缺省：无工程级声明时，整个工程按弱类型模式解释（P4）。
- 四元落点：**环境**（环境构造参数），不是结构属性——工程中的每个文件仍保持模式中立。
- 形式示意：入口文件头部的模式声明，如 `mode(strong);` 单独成条（结构形态，分号结尾）。

### 2. 区域级声明（`mode(P) { ... }`，局部显式）

- 形式：模式声明是**类型系统环境**提供的普通**操作**，以策略值为参数、花括号为被包裹结构：`mode(strong) { ... }` / `mode(weak) { ... }`——与 `if (cond) { ... }` 同族的「操作名(参数) { 体 }」形态（《语法设计》「括号与花括号是操作」）。
- 两种典型用途：
  1. **工程内局部覆盖**：工程整体强类型，某区域显式弱类型；
  2. **跨边界载入**：主程序载入一段独立的轻量脚本时，脚本内部用 `mode(weak) { ... }` 显式声明按弱类型模式解释；载入时从调用入口传入模式的另一种落点见后文「传入式调用」——两者都是 P11 的显式穿透标记（可审计）。
- 边界：`mode(weak) { ... }` 的结果回到外层（强类型）模式时，经过边界转换与运行时检查（`expect(T) { ... }`，见后文「expect 断言操作」）。
- 四元落点：**组合**（操作作用于值），与工程级声明共享同一策略值（P12、见前文「共享结构层」结构层唯一）。

### 3. 两级关系

- 工程级声明 = 环境的既定策略；区域级声明 = 结构内显式请求的局部解释，本质是穿透（P11）。
- 两者形式不同、粒度不同、四元落点不同，但引用同一组策略值（strong / weak）。
- 具体语法符号、入口文件的界定方式、边界转换的具体形式，留语法层与后续章节定义。

### 4. 边界转换的具体形式：expect 断言操作

- 形式：`expect(T) { ... }`——**类型系统环境**提供的**断言操作**，作用于（类型值 T，花括号体：被穿透的结构）——与 `if (cond) { ... }` 同族的「操作名(参数) { 体 }」形态。
- 语义：解释被穿透结构得到值 v，按后文「类型关系判定的机制」关系判定检查「v 的运行时类型用于 T 的位置成立」（相等或可替换）——依据是运行时类型信息（见后文「类型值在运行时保留」：类型值运行时保留，弱类型区域的值携带类型标签）；
- **边界转换不改变值**：expect 只确认 / 赋予类型身份，不做任何值变换（数值加宽等是另外的显式操作）——判定与转换分离（见前文「强」的定性）。
- 通过 → v 以类型 T 进入强类型模式；失败 → 产生诊断值（见前文「拒绝与诊断」：最近环境终止本次解释，诊断值沿组合层级向上传递）。
- **模式无关**（见前文「操作解释规则模式无关」）：expect 的检查是操作自身的解释规则，弱类型模式下同样可用（决策者自愿断言）。
- 这是 P11 条件②的落地形式。

### 5. 传入式调用：载入时传入模式

- 形式示意：`load(link, weak)`——载入操作 `load`（类型系统环境提供），作用于（脚本链接 link：String 值，该脚本的解释模式：策略值）；应用形态与 `print(...)` / `Person("Jack")` 同族；
- 语义：环境载入 link 指向的脚本结构，按传入的策略解释——脚本的解释模式有三种来源：**载入时传入、脚本内部声明、工程级声明**；优先级链（与 int 精度策略同构，见后文「原子类型值」）：**载入时传入 > 脚本内部声明 > 工程级声明 > 默认弱类型（P4）**——无传入时脚本内部声明生效，两者皆无时按工程级声明（工程级声明对整个工程生效，见前文「工程级声明」）；无工程级声明时按默认弱类型；
- 与 P11 的关系：**按工程级声明解释不构成穿透**——被载入脚本与工程同模式，无边界差异；**载入时显式传入（如 `load(link, weak)`）= 显式穿透标记**（决策者在调用入口显式声明被载入脚本的策略，可审计）；被载入脚本的结果回到外层（强类型）模式时，经 `expect(T) { ... }` 边界检查（见前文「expect 断言操作」）；
- 四元落点：load 是**操作**（环境提供，载入是环境的解释）；link 是 String 值；策略是值；
- **实现扩展**：本节确定形态与语义骨架，不要求最小实现立即支持载入——后续按此形态继续扩展实现；
- 必需性：想要的功能（外部脚本组合的既定方式）——非最小实现必需，但设计必须先有形态。

## 类型位置的结构层骨架

> 说明：本节规定类型的**结构落点**：类型直接写在声明结构里，标注组合已不再作为独立语法。

### 1. 类型位置：类型直接写在声明结构里

- 类型写在**可绑定位置的声明结构**里，类型前置（Java 式）：名称绑定 `int x = 1;`（《语言结构设计》「绑定」）、字段 `String name;` 与方法声明（参数 / 返回类型）（《语言结构设计》「类型声明」）、lambda 参数 `(int a) -> ...`（《语言结构设计》「操作构造：lambda」）；lambda 绑定不另写类型（lambda 自带参数类型 + return 决定返回类型，《语言结构设计》「操作构造：lambda」）；
- 四元落点：类型是**值**（P10），出现在声明结构中是结构的一部分——标注操作已退役，零新类别；
- lambda 返回类型不写：由体的 `return` 值决定（《语言结构设计》「操作构造：lambda」）。

### 2. 类型位置与绑定分离

- 绑定（`=` 操作）与类型位置（声明结构中的类型值）在结构上分离：`int x = 1;`——`int x` 是声明结构（类型 + 名称），`=` 是绑定操作；
- 好处：绑定结构保持模式中立；类型可独立存在（弱类型模式下透明、强类型模式下被检查）。

### 3. 类型位置 = 可绑定位置

- 类型写在「可绑定位置」的声明结构里：名称绑定 / 参数 / 返回 / 字段（见前文「检查对象」）——类型声明（《语言结构设计》「类型声明」）中的字段类型与方法声明（参数 / 返回类型）即这些位置的类型；
- 这些位置由语言环境的声明结构定义；本骨架声明依赖，但不在类型系统文档内定义声明结构本身（属语言结构层）。

### 4. 弱类型模式下的类型位置：透明

- 弱类型模式环境**认识**声明结构中的类型值，但**不响应**（见前文「类型位置在弱类型模式下的地位」）：解释 `int x = 1;` = 绑定 x → 1，类型值对结果透明，不检查、不诊断。

### 5. 类型值的形式

- 类型符号是字符串值；声明结构中的 `int` / `String` 等就是一个**类型值**。
- 类型值来自**类型系统环境**提供的原子类型值，或由类型构造操作生成（复合类型）——类型构造留类型宇宙章节。
- 结构中出现类型值不引入新语法类别（P10）。

### 6. 骨架边界（不在当前骨架内，后续扩展）

- 类型宇宙（类型值的值域：基础类型、复合类型）——下一章。
- 声明结构与绑定结构——语言结构层。

## 类型宇宙的骨架

> 说明：本节规定类型宇宙的**构成机制**：类型值从哪里来、如何构造、如何判定关系；具体类型清单与关系种类可按需要逐步扩展。

### 1. 类型宇宙的构成

- 类型宇宙 = **类型系统环境提供的原子类型值** + **类型构造操作**（产生复合类型值）。
- 全部落在四元本体论内：类型是**值**，类型构造是**操作**——不引入新类别（P10）。
- 「宇宙」不是封闭清单：环境可以注册新的原子类型值；新类型由构造操作组合而生（能力生长）。

### 2. 原子类型值

- 原子类型是**类型系统环境**提供的类型值（相对该环境不可再分，与《Origin Language 核心抽象设计》「组合」一章的原子相对性一致）。
- 设计原则：
  - 单一类型单一语义：不引入原始/包装分裂（如 int 与 Integer 只保留一种）；
  - 数值类型采用**语义性命名**（不与位数绑定）：
    - int（有符号整数）、long（更宽的有符号整数）——**精度是环境配置策略**，不写死在代码里：
      - 策略来源一：决策者在工程级声明中显式给出（见前文「模式声明的两级形式」机制）；
      - 策略来源二：**环境感知**——环境构造时读取底层环境参数（如操作系统位宽），按**预定义的策略表**（多策略模式）选择精度：环境内置一组精度策略，例如 8 位系统 int=8/long=16、32 位系统 int=32/long=64、64 位系统 int=32/long=64（64 位下 32 位 int 仍是最优选择）；**不采用「字长倍数」这类固定公式**；
      - **缺省 = 感知**（查策略表，跟随硬件），显式声明覆盖缺省；策略表可扩展——新硬件出现时增加策略行即可，不改代码；
      - **兜底**：极端情况下（无配置且无感知），启动默认策略——int = 32（以 32 位策略表行为基准，long = 64）；
      - 精度策略的优先级链：显式声明 > 环境感知（查表）> 默认策略；
      - 感知是环境对其它环境的穿透（广义）：其它环境的内容（此处为字长参数）进入当前环境，成为解释规则的一部分。注：《Origin Language 核心抽象设计》「穿透」一节定义的穿透是「其它环境的解释映射到当前环境」；此处取广义——其它环境的**内容**进入当前环境；
      - 未来硬件演进无需改代码、甚至无需改配置；源代码语义不变（结构保持、环境响应）；
    - float（单精度）、double（双精度）——名字即精度（IEEE 754）；
    - byte（8 位无符号）——字节是行业标准单位，语义即 8 位，不策略化。
  - 精度策略运行时不可变（P12 同构）；int / long 的溢出行为属操作层解释规则，不在此定义。
  - 与底层环境互操作需要定宽时，用**类型系统环境**提供的显式转换操作（操作名体现格式，如 64 位定宽编码）——语言类型宇宙不引入定宽类型名（与字符编码边界同构）。
  - boolean、String 等计算/存储必需的基础类型列入最小清单。
  - **成员依托类型值**：String 类型的成员（at 方法 / length 字段）是 String 类型值的载荷成分——环境为原子类型提供的类型声明（《语言结构设计》「类型声明」），不进入全局绑定表，成员不能脱离类型单独存在（形态见《语义设计》「字符串操作」）。
- **char 列入最小清单**：语义采用**扩展字形簇**（grapheme cluster，贴近人类直觉——显示是给人看的）：
  - 编码（UTF-8 / UTF-16 等）是表示层问题：类型层不承诺，环境内部自由；
  - char ↔ 字节序列的转换由**类型系统环境**提供的显式编码/解码操作完成，决策者在边界选择（操作即适配器，转换显式）；具体编码操作名在后续扩展中定义；
  - 字节级精确控制用 `byte` 类型 + 显式编码操作（字节是字节、字符是字符）；
  - 字符串的字符序列按字形簇定义——依赖字形簇**边界划分**规则（必需）；字形簇**排序**规则是扩展功能（字典序比较），可在后续版本中补充；
- 最小清单：int / long / float / double / byte / boolean / String / char。其余宽度与无符号变体按需由环境注册生长（宇宙不封闭），届时命名同样遵循语义性规则。

### 3. 类型构造操作（复合类型）

- 类型构造器 = **以类型为参数、产生新类型值的操作**——泛型即类型构造器，不引入新概念（P10）。
- 复合类型也是值：由构造操作作用于类型值生成，可继续作为参数参与构造（如 `(A -> B[])`）。
- **复合机制统一为一条：「组合被解释为类型」**——一个组合，其参数位置放的是类型值，被环境解释为类型描述。
- 最小清单：
  - 函数类型：`(A -> B)`（参数类型 A → 返回类型 B；多参数形式留语法层，骨架定「参数类型序列 + 返回类型」）；**无返回 = 返回类型位置省略**：`(A ->)` 表示接受 A、无返回——不引入占位类型（不用「一个值」表示「无值」）；
  - **结构形态类型**：组合本身就是聚合（核心层能力），结构类型 = 组合形态描述：字段名 = 操作名，字段类型 = 参数位置上的类型值（如 `(point (int x) (int y))`，类型前置与字段声明同向）——不另设独立的类型构造器类别；**同质重复形态（数组）是结构形态类型的特例**：`int[]` 描述「数组元素全部 int」——数组的类型检查 = 对重复形态的匹配判定（所有元素位置统一匹配 T）；数组类型形态 `T[]`——`[]` 是类型构造操作名（后缀形态，《语法设计》「文本环境对这些值的解释」第 7 条），类型宇宙不固定其它名字；容量提示 `T[N]`（《语义设计》「数组」）附着于声明、是实现层预留提示，**不参与类型判定**（`int[10]` 与 `int[]` 是同一类型值）；名义通过绑定操作把形态描述绑定到名字获得（`point-type = ...`）；
  - **类型声明**（《语言结构设计》「类型声明」）：`Name { ... }`——名称 + 花括号类型体，环境解释 = 构造携带字段与方法的名义结构类型值并绑定名称——「组合被解释为类型」的形态描述定字段，类型声明加方法；实例构造 = 类型值可应用（《语言结构设计》「实例构造与方法调用」，与数值转换同一机制）；
  - **泛型（类型参数）**：`Box<T> { ... }` 声明类型参数，实例化 = 类型构造器应用 `Box(int)`（类型值可应用——参数是类型值 → 产出类型值）——泛型即类型构造器（本机制）的形态落地（《语言结构设计》「类型声明」类型参数）；
- **设计依据（为何两种形态不再合并）**：函数类型描述**操作值**（操作元：输入→输出的作用），结构形态类型描述**组合值**（组合元：操作名 + 参数位的关系结构）——两者落在四元的不同元；机制已统一为一条（组合被解释为类型），形态两种是本体论要求的收敛极限。佐证：无返回（`(A ->)`）只属于函数类型——作用可以无产出，聚合不存在无产出。
- 后续扩展（不列入最小清单）：联合类型（sum type，Option / Result 的载体，与「无 null」配套）、集合 / 映射等——按需由环境注册。

### 4. 类型关系判定的机制

- 关系判定 = **类型系统环境**提供的**操作**，作用于两个类型值，产生判定结果（值）。
- 判定与转换分离（见前文「强」的定性）：关系判定只产生结论，不伴随任何转换。
- 判定结果供见前文「检查对象」的三类检查使用；「不成立」即触发诊断（见前文「拒绝与诊断」）。
- 关系集合——**相等** 与 **可替换**（组合推论，非独立声明关系）：
  - **相等**：类型值相等（结构相同）——类型是值，相等判定是核心能力；
  - **可替换**：v 的类型组合声明了 T——**直接或沿组合链传递**（`C + B`、`B + A` ⇒ C 对 A 成立）——且 T 的无体方法在 v 的类型中全部有实现（实现可来自成员提升，《语言结构设计》「类型声明」组合声明的名义推论，非结构推导）——判定：v 用于 T 的位置 ⇔ v 的类型 = T 或 v 的类型对 T 可替换；
  - **类型构造器应用与数组类型的参数位 = 不变**：`Box(Dog)` 用于 `Box(Animal)` 位置、`Dog[]` 用于 `Animal[]` 位置均不成立（只按相等判定）；
  - **数值类型之间无隐式关系**：int → long 等加宽必须显式转换（判定与转换分离，见前文「强」的定性）。
- 不在关系集合（留实现层）：类型—结构形态匹配（如 `int[]` 与具体数组的匹配）、泛型实例化（归入相等判定）。
- 具体符号与声明形式留语法层。

### 5. 类型值在运行时保留

- 类型是值；值在运行时存在。抹除类型 = 抹除值，与本体论冲突。
- 因此：类型值与其他值同等待遇，运行时不抹除（规避类型擦除的语义代价；运行期检查、穿透边界检查、对类型值的运行期操作都以类型值为依据）。
- 弱类型模式下类型值同样存在（不被检查，但仍可传递）。

### 6. 弱类型模式下的类型宇宙

- 类型构造操作在两种模式下都产生类型值（「认识」）；差异只在「类型值是否参与检查」——这是见前文「弱类型模式下的类型位置」「认识而不响应」在类型宇宙层的细化。
- 弱类型模式下：类型值不参与检查、不产生诊断，但可作为值存在与传递，不影响运行时解释结果。
