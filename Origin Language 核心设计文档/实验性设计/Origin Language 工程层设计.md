# Origin Language 工程层设计

## 定位：工程层 = 决策者组织多文件源代码集合的环境层

- 四元落点：工程层**不引入四元之外的新类别**——文件链接是 String 值；载入（load）是操作（环境提供，《类型系统设计》「传入式调用」）；工程策略（模式 / 精度）是环境构造参数（《类型系统设计》「工程级声明」/「原子类型值」）；「入口」是环境对载入请求的响应。
- 最小原则：工程层最小骨架只有三件实质内容——**入口文件界定、main 入口、load 载入**；名称空间最小 = 全局名称池（见后文「名称空间」）；工程配置最小 = 载入环境参数（见后文「工程配置」）。
- 不发明：模块、包、配置文件语法、构建产物格式——这些内容在后续扩展中再纳入（见后文「后续扩展」）。

## 入口文件

- 界定：**由载入环境指定**——启动方（载入环境）传入工程入口的文件链接，即入口文件；工程层不发明配置文件语法（《语法设计》「工程级声明」既有约定，本节正式落实）。
- 入口文件的特殊性：唯一可承载工程级声明的文件——`mode(P);` 出现在非入口文件 → 诊断（《类型系统设计》「工程级声明」/《语法设计》「工程级声明」）。
- 一个工程（一次启动）只有一个入口文件；其他文件经 `load(link, ...)` 载入（见后文「load 载入语义」）。

## main 入口

- 形态（与《语法设计》「顶层」一致）：
  - 函数声明：`main(String[] args) { ... }`——无返回 = 返回类型省略；
  - 或 lambda 绑定：`main = (String[] args) -> { ... };`；
- 形态约束（编译执行时检查）：单个参数、类型 `String[]`、无返回类型标注——不满足（如 `main()` 或 `int main(int x)`）→ 编译执行产生诊断；解释执行不检查（main 是普通名称）；
- lambda 绑定的 main（`main = (String[] args) -> { ... };`）同样受形态约束：体**不得 return 值**（与函数声明的「无返回」同义）——体有 return → 编译执行产生诊断；
- 参数：`args` 是启动方传入的**命令行参数序列**（String 数组）；无命令行参数 = 空数组；
- 重绑：顶层多次绑定 main → 沿用重绑规则，最后一次绑定生效；
- 位置：main 是普通顶层绑定，不要求是顶层最后一个值；
- 特殊性的边界：main 的特殊性**只在入口文件 + 编译执行时存在**——非入口文件中的 main、解释执行下的 main，一律是普通名称。

## 两种执行方式

- 同一源代码结构，两种执行方式皆可执行（**结构保持、环境响应**）——执行方式是工程层（载入环境）的选择，不改变源代码结构：
  - **编译执行**：入口文件顶层按序解释构造工程环境（模式声明、类型声明、函数声明、绑定等声明全部生效），识别 main 绑定为入口；顶层解释完成后**自动应用** `main(命令行参数序列)`——main 是程序的执行起点；
  - **解释执行**：顶层依次解释（《语法设计》「顶层」），main 是普通名称（普通绑定，不特殊、不自动调用）；要执行它 = 显式应用 `main(["a", "b"])`；
- 两种方式的唯一差别 = **是否在顶层解释完成后自动应用 main**；顶层各值的解释（含发生的作用）完全一致；
- 编译执行在入口文件找不到 main → 诊断。

## load 载入语义

- 四元落点：load 是**操作**（类型系统环境提供，《类型系统设计》「传入式调用」）；link 是 String 值（文件链接）；策略是值；载入 = 环境的解释；
- 位置：load 是普通操作，顶层与结构内皆可应用——同一操作、同一语义，不发明「只允许顶层」的位置规则；
- 链接解析：相对链接相对**该 load 所在文件的所在位置**解析；绝对链接直接使用；链接形态 = 文件路径字符串；
- 载入语义：
  1. 环境找到 link 指向的文本，解释为结构，按解释策略解释（优先级链：载入时传入 > 脚本内部声明 > 工程级声明 > 默认弱类型，《类型系统设计》「传入式调用」）；
  2. 被载入文件的顶层依次解释（与《语法设计》「顶层」同一种作用），顶层绑定进入**同一环境绑定表**（全局名称池，见后文「名称空间」）——载入完成后调用方可见其中的绑定；
  3. load 应用的产出 = 被载入文件顶层的解释结果（最后一个值的解释结果）；
  4. 幂等：同一次工程运行中，同一文件只载入解释一次——后续 load 解析到同一文件不重复解释，产出已载入的产物（循环载入的最小终止机制）；
- 策略参数可选：`load(link, weak)` = 载入时传入策略；`load(link)` = 不传策略，按优先级链落到脚本内部声明 / 工程级声明 / 默认弱类型（与《类型系统设计》「传入式调用」优先级链一致）；
- 与 main 的关系：被载入文件中的 main = 普通名称（见前文「main 入口」）；被载入文件中的工程级声明 `mode(P);` → 诊断（见前文「入口文件」）；
- 载入失败语义：link 找不到文件、被载入文本解释失败 → 诊断值（《语义设计》「操作失败的统一响应」），沿组合层级向上传递；
- 边界：被载入文件按优先级链得到策略（载入时传入 > 脚本内部声明 > 工程级声明 > 默认弱类型）；**按工程级声明解释时与工程同模式，不构成穿透**；载入时显式传入策略、或脚本内部声明与工程不同模式时构成 P11 显式穿透，回到强类型模式的边界检查经 `expect(T) { ... }`（《类型系统设计》「expect 断言操作」）；
- 实现扩展：按此形态与语义骨架继续扩展实现。

## 名称空间（最小：全局名称池）

- 载入的文件共享**同一个环境绑定表**——顶层绑定全局可见；
- 同名冲突沿用重绑规则（`=` 覆盖，无隔离机制）；
- 模块 / 名称隔离 / 前缀限定 → 后续扩展（见后文「后续扩展」）。

## 工程配置（最小：载入环境参数）

- int 精度策略等工程级参数由**载入环境传入**（与《类型系统设计》「原子类型值」的「环境感知」同构），与 `mode` 的优先级链同族：载入时传入 > 工程内声明 > 默认；
- 决策者在源代码中显式声明工程配置的形态（配置文件语法）→ 后续扩展（见后文「后续扩展」）。
