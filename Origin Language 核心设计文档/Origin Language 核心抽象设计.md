# Origin Language 核心抽象设计

> 核心定位：在最小抽象的基础上，保持结构稳定，并允许环境在不破坏根本关系的前提下继续生长能力。

## 文档导读

- 这份文档是《抽象与设计的基本原则》在编程语言设计上的应用展开。基本原则回答「是什么、为什么」，本文回答「在语言设计上这意味着什么」。
- `Origin` 是一个极简的抽象框架，而不是一套完整的现成语言定义。
- 它关心的是：值、操作、组合、环境，以及源代码（作为组合的形态）之间的关系，以及这些关系为何必须保持最小、显式与可解释。
- 它不承诺固化某种具体实现；它只承诺建立一个足够稳固的抽象锚点，供后续环境扩展。
- `Origin` 实际上是一个计算本体论的最小公理系统。

本文档回答的是：什么是 `Origin` 中不可删除的基本抽象；它们之间形成了什么样的最小闭合关系；原子性、观察层与环境之间是什么关系；哪些内容属于核心，哪些留给具体环境继续生长。

本文档**不定义**具体语法、类型系统、分支循环、模块系统、编译器、运行时、标准库或工程体系。这些内容可以建立在核心之上，但不能反过来成为核心的前提。

> 阅读提醒：本文档中的所有概念都不是固定层级的物理实体。当你读到任何一个概念时，请先问自己：我此刻站在哪个环境的视角？如果你发现自己在用一个环境中的规则去评判另一个环境中的行为，请停一下——那可能正是需要切换视角的信号。

## 设计哲学

### 1. 承认事实

`Origin` 的设计哲学首先要求承认事实：把「存在的事实」与「想要的功能」分开。物理法则直接描述自然界中的事实，数学是一种可以描述自然界的抽象语言，编程又产生于数学。因此，`Origin` 把"法则"本身作为抽象对象来理解——这体现在：最终解释权被交给环境，以及环境提供的原子值与原子操作。

很多人会自然地联想到安全、权限等问题，但这恰恰是把事实和功能混为一谈了。安全必须建立在事实的基础之上，因此这些功能都应该在后期根据需要再添加。

### 2. 最小必要性

> **没有定义，不需要证明其合理性；只有定义了一个东西，才需要证明它为什么必须存在。**

核心抽象只保留关系闭合所需的最小。一个概念不能仅仅因为"以后可能有用"而进入核心；判断它是否属于核心用删除实验：删除它，核心关系是否仍然闭合。这使核心的设计目标从"功能最少"变成：**关系闭合所需的最小**。我们不需要提前决定未来应该长成什么样——只要基本抽象足够稳定，新的能力就可以从它们之间的关系中继续生长。

### 3. 不预设具体实现

核心不规定：

- 数据如何存储；
- 值是否具有地址；
- 操作如何编码；
- 结构如何表示；
- 源代码必须是文本；
- 是否存在编译器；
- 是否存在解释器；
- 是否存在传统意义上的运行时。

宿主语言、语法、解析器、IR、运行时、平台后端以及自托管路径，都属于后续逐步生长的部分。

因此：

> **规则可以被抽离，抽象可以被继承，而具体规则由环境决定。**

核心需要建立的，是一个足够小、足够稳定、能够与现实发生关系的抽象锚点。

## 为什么要这样做

### 1. 组装式体系与扩展性

把不必要的功能解耦出去，会带来扩展性——核心从源代码层面看什么也没有，只有一些概念。

面对一个天马行空的需求，实际上只有两种可能：当前的环境或体系不支持（规则不允许），或者这样做非常困难（主观拒绝）。

如果我们不把不必要的规则放进核心，体系就可以保持组装性：真正限制某项能力的，不再是核心预先规定的边界，而是当前环境本身的规则；而 `Origin` 所说的"承认事实"，正是承认这些规则确实存在。

因此，最小核心的意义不是让体系拒绝一切需求，而是把"核心必然如此"与"具体环境希望如此"区分开来——前者是事实和基本关系，后者在环境中继续构造。只有先完成这种区分，体系才不会把某个具体实现误认为唯一可能的世界。

### 2. AI 时代的逻辑支点

AI 往往是迎合式的：它首先不会拒绝，而是寻找方法试图实现使用者的需求。但目前的 IT 世界技术碎片化太严重，AI 的思考是片段式的，又没有逻辑支点告诉 AI「这个东西触碰到了规则」。于是使用者陷入无限循环——依赖 AI，而 AI 一直在原地打转：它没有拒绝你，但就是无法给你想要的东西。

## 核心四元与不可约性

`Origin` 核心包含四个不可约的基本维度：

- **值**（Value）：可区分的存在；
- **操作**（Operation）：作用；
- **组合**（Composition）：操作作用于值形成的结构；
- **环境**（Environment）：提供解释，并规定观察边界。

它们不是四个彼此平行、互不相关的对象，而是一个最小闭合系统中的四个必要位置。

```text
                  环境
                /     \
               /       \
         规定观察边界   提供解释
             ↓           ↓
          值 ⇄ 操作
             \   /
              \ /
              组合
               │
               │ 换观察层
               ↓
              值
               │
               └────→ 操作 → 组合 → …
```

这不是程序执行流程，而是核心的**概念关系图**：值需要关系与作用，才能在与其他存在的差异中表现出可区分；操作需要存在，作为它作用的对象。二者相互需要——这正是「值 ⇄ 操作」。操作作用于值之后，形成组合；组合需要环境提供解释；环境提供的原子值与原子操作，又恰恰是值与操作。四个位置首尾相接，形成一个闭合的环。

说它们不可约，用删除实验检验：删除其中任意一个位置，看整个关系是否还能保持闭合。

**删除`值`。** 操作失去可以作用、关联与区分的对象；组合失去参与者；环境失去可解释的基本存在。如果重新引入「对象」「实体」等概念来承担这些职责，本质上只是重新定义值。因此值不可删除。

**删除`操作`。** 可区分性是值的第一性质，而它必须经由关系与作用才能表现出来。删除了操作，值的可区分性就无法被识别——值作为可区分的存在失去意义。如果引入「变化」「动作」等概念恢复这一能力，本质上又重新引入了操作。因此操作不可删除。

**删除`组合`。** 值与操作可以分别存在，但二者形成的结构没有独立的承载位置；更重要的是，无法解释一个结构如何在另一个观察层作为整体重新成为值。如果用「关系」「结构」等概念恢复这一能力，只是给组合换了名字。因此组合不可删除。

**删除`环境`。** 原子的界定失去基础；操作的意义必须由核心自己规定；组合无法获得解释。这样一来，结构与解释被迫由同一个位置承担——而整个设计，正是为了把这两者分开。因此环境不可删除。

删除实验的结论是：四元中的每一个位置都不可删除。这不是因为偏爱这四个概念，而是因为删除任何一个，闭合关系上都会留下缺口；而补上缺口的东西，只会是它自己。

图中「换观察层」的含义——组合在另一观察层被整体承认为原子，再次进入操作与组合——将在组合一章说明。

## 值

值是有可区分性的存在。可区分性靠什么办法成立，本文不规定；区分策略由环境提供。语言设计上需要补充的是：

**值不是某一种具体的数据表示。** 计算机中的一切最终都可以表现为数据，但值首先是一种抽象。一个存在能够成为值，是因为它能够与其他存在区分开来。

可区分性可以通过「位置」来帮助理解——这里的位置不是物理地址，而是一种抽象意义上的位置：

- 内存地址可以被理解为数据在内存中的位置；
- 实体 ID 可以被理解为实体在数据库中的位置；
- `x = x + 1` 中的两个 `x`，名称相同，但处于不同的位置，承担不同的关系。

这些例子不是为了规定值必须拥有地址，而是为了帮助理解：一个值必须能够被区分。

值不规定：存储位置、内存地址、数据结构、具体类型、物理表示。这些内容属于具体环境。但环境必须提供某种可操作的唯一性锚点，否则操作无法发生。

## 操作

操作是一种作用，具有方向性和连接性；操作的核心是作用本身而不是结果；操作本身也是一个值。语言设计上需要补充的是：

当操作正在作用时，它处在操作的位置；当它被作为整体看待时，它处在值的位置。这两个位置不会同时发生——正在作用的操作是操作，被看待的操作是值。

**示例：1 + 2 = 3**

在计算器环境中，`1 + 2` 是一个组合，`+` 操作不但体现了连接性，还描述了连接关系。这个加法并没有被立即执行；只有当 `=` 这个操作作用于 `1 + 2` 这个结构时，才会返回 `3` 这个值。

## 组合

组合是操作作用于值形成的结构；组合的产物也是值；组合只负责把关系保持下来，效果由环境解释。语言设计上需要补充的是：

汇编代码由 CPU 指令集解释；C 代码则由更底层的环境逐层解释。组合本身不携带最终如何产生效果的答案——它首先只是一个结构。

原子性不是绝对属性，而是相对于环境的。设环境 `E₁` 将 `A` 和 `O` 视为原子：

```text
E₁：
A → 值
O → 操作
```

当它们形成 `C = O(A)`，`C` 对 `E₁` 而言是组合。如果另一个环境 `E₂` 将 `C` 作为整体识别：

```text
E₂：
C → 值
```

那么 `C` 在 `E₂` 中就获得了值的地位。"是组合"与"是值"并不构成绝对互斥，它们可以属于不同观察层。

四元关系因此不是单向链，而是一个可以在观察层之间继续套入自身的结构：

```text
┌──────────────────────────────┐
│ 环境₁                       │
│                              │
│   值 + 操作                  │
│          ↓                   │
│        组合                  │
└──────────┬───────────────────┘
           │ 整体观察
           ↓
┌──────────────────────────────┐
│ 环境₂                       │
│                              │
│      组合 = 值               │
│              ↓               │
│           操作               │
│              ↓               │
│           组合               │
└──────────┬───────────────────┘
           │
           ↓
          ……
```

这个"套圈"不是无限递归地定义概念，而是允许同一结构在不同观察层获得不同的原子性地位。这正是 `Origin` 保持结构稳定并允许环境继续生长的重要基础。

组合的不可删除性，删除实验已经证明。它更深一层的原因正是上面的套圈结构：组合是不同观察层之间发生整体化与重新原子化的结构载体——没有组合，一个由当前层多个单位形成的结构，就无法在更高观察层重新成为值，也就无法进入新的操作与组合。

## 环境

环境提供解释，并规定观察边界；环境提供原子值、原子操作与解释；环境本身也是值。语言设计上需要补充的是：

**环境是抽象与现实发生联系的必要条件。** CPU 指令为什么产生某种行为？C 语言中的操作为什么最终产生这样的机器行为？这些问题都需要环境。脱离环境讨论具体行为，本身就没有意义。

环境也可以被理解成一种抽象。CPU 可以提供代码运行环境；CPU 本身首先是一个抽象概念，不同型号的 CPU 可以看作这个抽象的具体实现。汇编语言也是类似的：它可以作为一种环境，为更高层提供规则和原子操作；但从另一个层次看，汇编语言本身又是数据，是值。值、操作和环境并不是彼此完全隔离的东西，它们是在不同观察层次下对现实结构的不同抽象。

将环境视为值，并不要求环境在运行时自证其存在。当某个环境作为解释者工作时，它只负责解释当前结构，不需要同时解释自身；只有当一个更底层的环境主动将它作为可操作的数据时，它才在那个观察层表现出值的属性。解释者视角与被观察者视角并不是同时对同一层发生的，因此不会形成递归依赖。

环境的核心作用，是提供原子值、原子操作以及解释规则。这里所说的"原子"是相对于当前环境的边界声明：一个操作在该环境内不可再分，即视为原子；它在底层环境可能由多个操作组合而成，但这不影响其在上层环境中的原子性。

从底层来说，CPU 提供指令集；在 CPU 之上，汇编语言可以形成另一层环境；再往上，C 语言又可以形成另外一层环境。可以用 **CPU → 汇编 → C** 来帮助理解环境之间的继承和构造关系。但这里的"层"主要是一种理解方式：环境并不一定必须形成严格的树状结构，环境之间可以存在继承、组合、嵌套以及其他解释关系。真正重要的是：环境决定某个结构如何被解释。同一个结构进入不同环境之后，不一定产生完全相同的效果。

环境承担两个基本角色：**第一，提供当前层的原子性单位**——环境提供或承认当前层的原子值与原子操作；**第二，解释结构**——当值与操作形成组合时，环境按照自己的原子规则和观察边界对它进行解释。这里的"解释"并不是四元之外的第五种基本实体：解释本身仍然落在"操作"这一元——它是环境提供的一种操作，作用于组合，并产生一个值。至于这个解释操作在更底层如何成立，属于另一个观察层的问题。

这使得相同结构可以在不同环境中获得不同的具体意义，而不必修改结构本身。这里的"环境"不应狭义理解为某个运行时、进程、虚拟机或操作系统——这些都只是具体环境的一种实现方式。核心所说的"环境"更抽象：它是抽象结构获得具体解释的必要基础，同时规定当前观察层的边界。

**未解释与拒绝解释的落点。** 当环境无法解释，或者明确拒绝解释一个组合时，四元关系仍然需要有一个落点——否则环境一旦遇到不能处理的结构，核心关系就会在失败处中断。这个落点仍然是值：环境可以产生一个承载"未解释"这一事实的值，例如 `Unknown` 锚点。它不是崩溃，也不是某种特殊的"非值"，而是一个普通值，只是它携带的语义是"本次解释尚未发生，或者已经被当前环境拒绝"。

```text
组合 → 环境 → 值（普通结果，或承载"未解释 / 已拒绝"的值）
```

这里的 `Unknown` 只是"未解释值"的一种具体示例，并不是额外引入的基本实体。后文的 Lua 示例会从值的角度进一步说明它为什么可以作为公共锚点。

## 观察层、排他与穿透

**解释的排他。** 同一个值，在同一时刻，只被一个环境解释。

换一个时刻，另一个环境也可以解释它——两个环境先后各自解释同一个结构，每一次解释都只完整地属于其中一个环境。这正是"结构保持，环境生长"：结构不变，解释随环境而不同。

即使有其它环境的解释被允许进入当前环境，这一点也不改变：解释的内容仍由它所属的环境承担。

**穿透。** 环境之间可以存在各种关系：一个环境解释另一个环境产生的结构；一个环境把另一个环境视为整体值；一个环境构造另一个环境。本章讨论其中一种：穿透。

一个环境，是否只能使用自己直接提供的解释？不一定。如果当前环境允许，其它环境的解释可以进入当前环境。这就是穿透。

> **穿透，是将其它环境的解释映射到当前环境的一种行为。**

是否允许穿透，由正在解释这个结构的环境决定。环境可以允许，也可以禁止。

例如，在 CPU、汇编、C 这样的环境关系中，如果相关环境都允许直接使用 CPU 指令，那么 C 就可以穿透自身环境而直接使用 CPU 指令集。同样，如果 C 允许直接使用汇编，那么 C 中也可以出现能够穿透 C 环境的汇编代码。

这个例子只说明其它环境的解释如何被允许进入当前环境，不意味着当前环境的观察边界被取消，也不意味着所有其它环境的解释都会自动进入当前环境。因此，环境不是绝对封闭的容器，它可以决定哪些其它环境的解释能够进入当前环境。

穿透发生时，当前环境解释的只是映射本身——把它识别为来自其它环境的解释；映射过来的解释，其内容仍由它所属的环境承担。

穿透是什么：它是环境之间的一种具体关系，不是本文要引入的新基本概念。穿透用到的环境、解释与映射，都已经在四元之内；它只是已有元素之间的一种具体组合，不需要新增任何概念。因此，环境可以在不破坏四元关系的情况下，通过穿透获得自身所没有的解释能力。

## Origin、决策者与环境

`Origin` 并不是站在所有环境之上的最终观察者，而是首先存在于某个既定环境之中。对于 `Origin` 来说，当前环境是既定条件：`Origin` 无法直接决定自己当前所处环境的规则；它可以创造环境，但那属于创造之后发生的事情。因此：

> **在当前环境中，`Origin` 是被动的；在创造新的环境之后，`Origin` 才可能成为环境的构造者。**

**语义主权属于决策者。** 先给决策者一个位置：决策者落在"环境"元，它是环境的一个角色——环境中解释主动行为的一方。环境中的解释工作分成两部分：主动行为由决策者解释，被动行为由环境的其余部分解释；哪些行为算主动、哪些算被动，由环境界定。先有环境的划分，后有决策者承担主动行为的解释——因此决策者的语义主权范围，由环境划定。

把位置落到 `Origin` 上，需要区分三件事：核心规定不可约的基本关系，环境依据自己的规则解释结构，决策者则构造源代码并选择环境。源代码是否提交给某个环境解释，以及是否接受该环境给出的解释结果，也由决策者决定。这些正是决策者的主动行为，由决策者自己解释。

这不是把责任推到体系之外，而是承认一个边界：决策者的目标不由核心替它决定。把这个外部决定强行写进核心，反而会把某一种具体愿望误认为存在本身的规则。

例如，安全权限可以因为外部需求而被添加到一个环境中，但它并不是 `Origin` 核心天然拥有的属性。是否需要安全权限、采用什么权限规则，首先是决策者面对现实之后作出的选择，随后才会成为某个具体环境中的功能。

## 源代码

### 1. 最小的源代码就是一个组合

当我们需要描述组合关系时，就出现了源代码。

因此：

> **最小的源代码就是一个组合。**

源代码描述值、操作以及它们之间形成的关系。从核心的抽象角度看，最小的源代码就是这个组合本身；在实际环境中，当这种关系结构被记录下来，并能够被提交给某个环境继续观察或解释时，它就具有了源代码的意义。

由此，源代码不是第五个核心抽象，而是**组合**在跨环境描述和迁移时所呈现的形态。它仍然是组合，只是这种组合已经成为可以被保存、传递，并被不同环境重新观察的结构。

### 2. 源代码既被环境解释，又可以构造环境

除了描述组合之外，源代码还可以反过来参与环境的构造。前面说的是环境如何解释源代码，下面讨论的是源代码如何通过当前环境中的组合和操作，形成新的环境。

因为计算机语言本身也是由源代码构造出来的。

汇编语言存在源代码；

C 语言可以构造虚拟机；

Java 虚拟机本身就是一种环境，而它可以由 C 语言构造。

因此：

> **源代码既被环境解释，又可以构造新的环境。**

这使得源代码和环境之间不是单向关系。

环境解释源代码；

源代码又构造环境。

> 需要区分两类环境变动：
>（1）构造——源代码在当前环境中运行，通过组合和操作创建出一个新的逻辑环境，该环境自此作为当前环境的子层或邻近层存在；
>（2）选择/切换——决策者将同一份源代码（或其中的结构）提交给另一个已经存在的环境去解释，这属于部署行为，不由源代码本身决定。
>前者是计算过程的一部分，后者是主权决策的一部分。`Origin` 核心只关注前者，不替后者承担责任。

### 3. 源代码的跨环境性

如果源代码始终处于某个环境之中，那么为什么同样的源代码又可以在不同环境中存在？

例如，同样的 C 语言源代码可以在不同架构的 CPU 上运行。

原因并不是不同 CPU 必须拥有完全相同的实现。

而是：

> **源代码所描述的结构可以保持，而环境可以改变对这个结构的解释方式。**

不同架构的环境可以通过不同的底层环境，把同一个源代码结构转换成自己能够解释的形式。

因此，源代码在某个层面上具有环境无关性。

但这里的环境无关性并不是说源代码完全不受环境影响。

源代码始终处于环境中，也始终受到环境的影响。

真正保持不变的，是：

> **结构。**

### 4. 抽象源代码不是需求清单

因此，抽象源代码更准确地说，是：

> **一组关系结构的数学描述。**

它不是一份向环境索要能力的需求清单。

它不需要声明：

> 我要求环境必须拥有 X、Y、Z 能力。

它只是描述：

> 哪些值存在，哪些操作存在，以及这些值和操作之间形成了怎样的关系。

例如：

> A 操作以 B 为输入，产生 C。

首先描述的是一个结构。

至于这个结构：

- 在什么环境中被激活；
- 由什么规则解释；
- 被赋予什么物理意义；
- 最终产生什么效果；

都是环境自己的事情。

因此，不同环境能够解释同一个源代码结构，并不意味着它们必须实现一个共同接口。

而是因为：

> **它们各自的原子规则能够与这个结构发生对应。**

### 5. 结构不变，环境响应

这也是 `Origin` 抽象设计最重要的价值之一：核心保持结构，环境则可以在不破坏核心关系的前提下继续生长。

今天，环境 A 的原子规则能够解释某个结构。

未来，环境 D 的规则发生增强，也可能能够解释同一个结构。

源代码本身不需要改变。

改变的是：

> **环境对这个结构的响应策略。**

因此：

> **结构保持不变，环境可以继续生长。**

这就是 `Origin` 所说的"能力生长"。

新的能力不一定需要修改最初的抽象。

只要环境不断增加自己的原子规则，就可能产生新的解释能力。

因此，`Origin` 追求的并不是：

> 提前定义所有可能的能力。

而是：

> **建立一个足够小的结构，使新的能力能够从环境与结构之间的关系中自然出现。**

## 编译器

前文讨论的是环境与结构之间的抽象关系。进入具体实现时，编译器可以成为实现这种关系的一种方式，但它不是核心关系本身。

编译器不是 `Origin` 核心必须预先规定的概念。

很多时候，编译器所做的事情就是：

> **将抽象源代码描述的结构转换成底层环境能够解释的数据。**

因此可以形成：

**抽象结构 → 编译转换 → 底层环境可解释的数据**

但这只是众多可能实现方式中的一种。

`Origin` 的核心并不依赖某一种编译器结构。

## Origin 的整体关系

因此，`Origin` 并不是从一开始就规定一个完整的语言世界。下面的关系链是对前文概念关系的线性展开，不是程序执行顺序，也不是四元之间的时间顺序。

它从一个非常小的起点开始：

**值**

↓

值能够被区分。

**操作**

↓

操作使值发生作用。

**环境**

↓

环境提供原子值、原子操作以及解释规则。

**组合**

↓

值和操作形成关系。

**源代码（组合的形态）**

↓

源代码描述这些关系。

同时：

**源代码 → 构造环境**

而新的环境又能够：

**解释 → 源代码**

于是形成一个可以不断继续生长的闭环。

最终：

> **结构可以保持，环境可以生长；源代码可以描述结构，也可以参与构造新的环境。**

这就是 `Origin` 的核心。

它不是试图预先定义一个完整的世界。

而是定义一个足够小的起点，使新的世界能够不断从这个起点之上构造出来。

最终抽象图：

```text
                         环境
                    ┌────────┴────────┐
                    │                 │
              当前观察边界         具体解释
                    │                 │
                    ↓                 ↑
                 值 ⇄ 操作
                    │       │
                    └───┬───┘
                        ↓
                      组合
                        │
                        │ 整体观察
                        ↓
                       值
                        │
                        ↓
                      操作
                        │
                        ↓
                      组合
                        │
                        ↓
                       …
```

这张图表达的不是"程序从上往下执行"，而是：

> **一个观察层中的原子存在与作用形成结构；结构可以在另一观察层重新作为整体被观察；重新获得值地位后，它又可以进入新的操作与组合。环境则决定每一层的观察边界，并为结构提供具体解释。**

## 基于 Lua 语言表示的 Origin 最小核心示例

注意：这只是个示例，示例中的 `interpret` 函数并不是一个编译器或解释器的完整实现，而是 `Origin` 核心关系的直接映射：它将一个结构（input）交给一个操作（operation），由该操作决定该结构在当前环境中如何被解释。`interpret` 本身不做任何转换、不做任何优化、不附加任何规则——它只是一个汇聚点，把"结构"和"作用于结构的操作"这两个核心关系缝合在一起。解释行为不是被定义出来的，是在环境中生长出来的。这段代码展示了那个生长起点的最小形态。

```lua
-- Unknown 首先是一个普通值：它承载"未解释 / 原初"这一语义，而非值的容器或基类。
-- 它不包含其他值，也不被其他值继承。
-- 它仅仅声明一个事实：在这个抽象空间中，值作为可区分的存在而成立。
-- 所有值都与 Unknown 处于同一层面，不存在层级或派生关系。
-- Unknown 的声明看似"空"，但这种空不是无意义——它是不携带预设语义的状态。
-- 当环境没有类型系统时，Unknown 可以代表"未知含义的值"；
-- 在返回空值、处理空指针、类型渐进或类型转换时，它又可以由环境赋予其他角色。
-- Unknown 本身不定义这些角色，它只是为这些角色提供一个可被区分、可被操作的锚点。
-- 在具体实现中，Unknown 应当保持为跨环境可识别的公共锚点，
-- 而非各环境私有的内部标记。
Unknown = {}

-- interpret 不完成任何转换或优化。
-- 它只做一件事：将结构（input）交给操作（operation），由环境决定如何解释。
-- 这正是"环境解释结构"这一核心关系的直接映射。
-- 环境在这里不显式出现——它体现在 operation 的解释行为中。
function interpret(input, operation)
    return operation(input)
end
```
