# Origin Language：实现者指南

> 设计目标：将核心抽象设计落地为可实现的环境设计原则，帮助实现者决定原子值、原子操作、解释规则与边界行为。

## 文档导读

- 这份文档回答的是“怎么用”：如何基于 `Origin` 抽象构造一个具体环境。
- 它不规定一套唯一标准答案，而是提供实现者必须面对的关键问题和合理设计方向。
- 核心要求是：保持核心抽象关系不失真，同时允许不同环境以不同方式解释同一结构。

## 前言

这份文档是《Origin Language 核心抽象设计》的配套指南。

核心抽象设计文档定义了 `Origin` 的 **“是什么”** ——它描述了一个足够小的核心抽象，并说明了值、操作、环境、组合、源代码之间的关系。

这份指南则试图回答 **“怎么用”** ——如果你要基于 `Origin` 的抽象去构造一个具体的环境（一个编译器、一个解释器、一个虚拟机、一个 DSL，或一个运行时的中间层），你需要面对哪些实际问题，以及 `Origin` 核心期望你如何处理这些问题。

和核心抽象设计一样，这份指南不提供“标准答案”。它不会规定你必须使用 LR(1) 解析器还是 PEG，不会规定你的字节码格式，不会规定你的内存模型。它只做两件事：

1. **提醒你哪些问题是实现者必须面对的；**
2. **提供 Origin 抽象框架内合理的处理方向，供你选择或借鉴。**

> 每一个“方向”都只是建议，不是约束。如果你的环境有充分的理由偏离建议，只要保持对核心抽象关系的尊重，那就是合理的设计选择。


## 从抽象到具体：第一步的选择

当你决定基于 `Origin` 构造一个环境时，你首先面临的问题不是“怎么写代码”，而是：

**我的环境将以什么为原子起点？**

核心抽象设计中的“值”和“操作”都是哲学层面的描述。在具体实现中，你必须给它们一个落点。

### 1. 可选的落点方向

- **物理方向**：以 CPU 指令集、内存寻址、系统调用为原子起点。适合操作系统、嵌入式运行时的构造者。
- **逻辑方向**：以某个宿主语言的对象模型、函数调用约定、异常处理机制为原子起点。适合在现有运行时之上构造 DSL 或解释器的实现者。
- **混合方向**：以一组对外部服务（数据库、网络、文件系统）的操作为原子起点。适合构建领域特定的分布式计算环境。

无论选择哪个方向，`Origin` 只要求你做到一件事：

> **在你的环境中，每个原子操作必须具有明确的“可发生作用”的边界。环境不能提供模糊的、依赖外部猜测才能确定行为的基本动作。**

### 2. 值得思考的细节

- 你的原子值如何被区分？内存地址？句柄？URI？不可变内容的哈希值？
- 你的原子操作在作用于值之后，副作用如何被感知或隔离？
- 如果一个原子操作在其底层环境中失败了（比如系统调用返回错误），你如何将这个现实映射回 `Origin` 的抽象关系？


## 关于“结构”的具体化

核心抽象设计中，源代码被定义为“描述组合关系”的载体，而“组合”本身是一个关系结构。

在实现时，你**必须**为这个关系结构选择一个具体的表现形式。这是实现者最重要的决策之一。

### 1. 常见的表现形式

- **S-表达式 / AST**：结构以嵌套树的形式呈现。优点是对人类可读，易于遍历。缺点是树结构在表达交叉引用（如 GOTO、控制流图）时不够直接。
- **有向图 / 数据流图**：结构以节点（值/操作）和边（数据流向或控制依赖）呈现。优点是表达能力更强，适合编译器后端优化。缺点是描述形式更复杂，对编写源代码的人类不友好，通常需要前端语法树转换为这个形态。
- **文本行 + 约定缩进**：结构通过空格和换行隐含。优点是极简，缺点是解析规则容易产生歧义，对环境的解释能力要求较高。

### 2. 选择时的权衡

- 如果目标是让**人类直接编写**源代码，结构表现形式应当尽可能清晰、一致、易于学习。
- 如果目标是让**机器或工具链（如 IDE、分析器）** 处理源代码，结构表现形式应当具有明确的形式化定义（如可枚举的节点类型、确定的嵌套规则）。
- 同一环境可以接受多种结构表现形式（例如既支持二进制 AST 也支持可读文本）。`Origin` 不禁止，但实现者需要处理好它们之间的映射关系。

> Origin 核心不规定结构的表现形式，但它要求：**同一份结构描述，在当前环境中重复解释时，应产生一致的结果**（除非环境本身随时间发生了有意的、可解释的变化）。这是一个隐式的“确定性”要求。


## 关于 Unknown 的定位：你作为环境的态度

核心抽象设计中对 `Unknown` 的定义是“原初抽象标记”。在具体实现中，它会在多个场景中出现：

- 作为**空值 / 空类型**的占位；
- 作为**类型信息缺失**时，环境猜测或推迟类型检查的标记；
- 作为**渐进式类型系统**中，从“动态”向“静态”过渡的锚点；
- 作为**跨环境传递数据**但无法确定其格式或语义时的安全阀。

你作为环境实现者，不必在所有场景中给予 `Unknown` 相同的处理方式。但 `Origin` 期望你做到以下两点之一：

1. **明确你的环境对 `Unknown` 的解释策略**，并将这个策略作为环境行为的一部分，让决策者（程序员）可以预期；
2. **将 `Unknown` 当作运行时错误触发条件**——即，如果当前环境中，一个 `Unknown` 无法被确定性地解释为某种可操作的值，环境应当明确反馈，而不是静默地将其转换为一个任意值。

> 第二种策略是更安全的。如果你选择第一种策略（即赋予 `Unknown` 特定语义），请确保这种赋予是可追溯的、由环境显式声明的。


## 关于穿透的设计考量

穿透是 `Origin` 中最具“权力”的关系。它允许其它环境的规则进入当前环境。

核心抽象设计只定义了穿透的**存在性**和**控制权归属**（由正在解释这个结构的环境决定）。在具体实现中，你需要补充以下信息：

### 1. 穿透的生效范围

- **全局穿透**：环境在解释所有结构时，都允许其它环境的规则进入。优点是方便，缺点是安全边界模糊。
- **显式标记穿透**：源代码中使用特定标记（如某种关键字、特殊语法）来声明“此处允许穿透”。优点是可审计，缺点是需要额外的语法约定。
- **类型驱动穿透**：当某个值的类型在当前环境中无定义，但在其它环境中有定义时，自动触发穿透。优点是平滑，缺点是透明度过高，决策者可能无法预判。

### 2. 穿透失败时的行为

当被穿透的环境无法解释当前结构时（例如，该环境缺失对应的原子操作），当前环境应如何响应？

- 回退到当前环境自身的解释路径，并给出警告；
- 直接报错，要求决策者修改源代码或重新选择环境；
- 尝试通过第三环境进行中转解释（如果存在）。

> Origin 核心不规定失败策略，但建议：**穿透失败时，环境应给出明确的、可定位到具体结构和具体来源规则的信息**，而不是静默失败或模糊错误。


## 关于能力生长：如何设计可扩展的原子规则

`Origin` 的核心承诺之一是“能力可以从环境与结构的关系中生长出来”。这句话在核心抽象设计层面是自洽的，但在实现层面，你需要主动设计“可生长”的机制。

### 1. 建议的设计模式

- **模块化原子规则注册**：将原子操作视为可注册的单元。环境启动时加载一组核心原子规则；之后可以通过源代码构造或外部配置注入新的原子规则。这样，“生长”变成了“注册”的延续，而不是修改环境本身。
- **规则优先级链**：当同一个结构可以被多个原子规则解释时（例如，同一个 `+` 既可以是整数加法，也可以是浮点数加法，也可以是字符串拼接），环境需要定义一个优先级或歧义消解策略。优先级链本身可以随“能力生长”而动态调整。
- **元原子操作**：提供一组用于操作原子规则本身的操作（例如“查询当前环境注册了哪些原子操作”、“将一个原子操作替换为另一个原子操作”）。这会让环境具备“自我审视”的能力，是实现自托管路径的基础。

> 元原子操作的引入应当克制。只有在你的环境需要支持“在运行时修改自身解释规则”这一明确需求时，才引入它们。否则，保持原子规则的静态或半静态性质，可以让环境更稳定、更容易验证。


## 关于错误和边界情况

核心抽象设计没有定义错误处理，因为错误是环境的责任。但在具体实现中，错误是无法回避的。

### 1. 至少应当处理的边界情况

- **对不存在的值进行操作**：如果环境无法定位决策者指定的值，环境应该如何告知决策者？
- **歧义结构**：如果同一段源代码结构在当前环境下有不止一种合法解释（例如，`a - b - c` 可能是左结合也可能被理解为右结合），环境需要选择一个解释路径，或要求决策者提供消歧信息。
- **资源耗尽**：如果环境内部的资源（内存、文件句柄、网络连接）耗尽，一个原子操作无法完成，环境应当保留多少现场信息供决策者定位问题？

### 2. 一个值得参考的方向

将错误视为**环境向决策者返回的一种特殊值**，而不是一种“环境崩溃”或“未定义行为”。这个特殊值可以被结构中的更高层操作捕获或传递，从而将错误处理也纳入组合关系的描述范围，而不是排除在外。


## 关于文档的承诺

最后，`Origin` 不是一个强制标准。如果你的环境采用了这份指南中的某些建议，也偏离了其中一些，只要你的环境能清楚地回答以下三个问题，它就是合格的 `Origin` 实现：

1. **你的原子值和原子操作是什么？** ——决策者应当能够在开始编写源代码之前就知道。
2. **你的环境如何解释组合关系？** ——给定一个结构，环境产生什么行为，应当是可预期的，至少是可回溯的。
3. **你如何处理环境边界（穿透、选择/切换）？** ——决策者需要知道，他们的源代码在什么条件下会被当前环境接受，在什么条件下会被拒绝或产生不可预期的行为。

回答这三个问题的文档，就是你的环境自己的“实现者指南”。


## 结语

这份指南无法穷尽所有具体环境的需求。它的存在是为了让你在从“核心抽象设计”走向“具体实现”的过程中，少一些迷茫，多一些结构化的思考方向。

如果你在实现过程中发现 `Origin` 的核心抽象设计本身存在无法跨越的障碍——那不是你的错，那意味着核心抽象设计需要被补充或修正。原点可以移动，但移动的动机必须是现实需求，而不是理论推演。

愿你的环境在 `Origin` 之上长成它应有的样子。


# 附录：一个最小的示例环境

本附录展示一个基于 `Origin` 抽象概念构造的极小示例环境。它的目的不是作为 `Origin` 的参考实现或推荐范式，而是演示一条**从抽象到具体的映射路径**——即如何将核心抽象设计中的核心概念（值、操作、环境、组合、源代码）对应到真实代码中。

实现者可以参考这条路径，但完全不必照做。你的环境可以用任何语言、任何数据结构、任何解释策略来实现自己的设计选择。

> 本例使用 JavaScript 编写，因为它在概念上足够简洁，且无需额外工具即可运行和理解。如果你偏好其他语言，同样的结构可以很容易地迁移过去。


## 环境定义

`MiniEnv` 是一个极简环境。它包含两部分：
- **原子操作注册表**（`ops`）：一组可被调用的函数。
- **解释器**（`evaluate`）：接收结构，递归解释，返回结果。

```javascript
// ============================================================
// 0. 公共锚点定义（可跨环境共享）
// ============================================================

// Unknown 是值的原初抽象标记。
// 任何基于 Origin 构造的环境都可以识别它。
// 它本身不携带语义，但它作为锚点，可以将不可解释的结构
// 以可区分、可传递的形式继续承载。
const Unknown = {};

// ============================================================
// 1. 原子操作注册表（环境的核心）
// ============================================================

const MiniEnv = {
  ops: {
    // 加法：两个操作数相加
    add: (a, b) => a + b,
    // 减法：两个操作数相减
    sub: (a, b) => a - b,
    // 条件：如果第一个操作数为真，返回第二个，否则返回第三个
    if: (cond, thenVal, elseVal) => cond ? thenVal : elseVal,
    // 打印：输出值并返回它本身（副作用操作）
    print: (val) => { console.log(val); return val; }
  },

  // ============================================================
  // 2. 解释器：将结构转化为动作
  // ============================================================
  evaluate: function(struct) {
    // 如果结构不是数组，它就是一个原子值（数字、字符串等）
    if (!Array.isArray(struct)) {
      return struct;
    }

    // 结构是数组：[操作名, 参数1, 参数2, ...]
    const [opName, ...args] = struct;

    // 递归解释所有参数（先求值参数）
    const evaluatedArgs = args.map(arg => this.evaluate(arg));

    // 查找原子操作
    const operation = this.ops[opName];
    if (typeof operation === 'function') {
      // 操作发生作用（核心：动作在此执行）
      return operation(...evaluatedArgs);
    } else {
      // 返回一个携带 Unknown 标记的结构
      // Unknown 是公共锚点，任何 Origin 环境都能识别
      return {
        anchor: Unknown,   // 公共锚点
        op: opName,         // 上下文信息（可选）
        args: evaluatedArgs // 上下文信息（可选）
      };
    }
  }
};
```

## 使用示例

示例 1：简单加法

```javascript
// 源代码结构：描述关系，而不携带执行规则
const source = [
  'add', 1, 2
];

// 环境解释结构
const result = MiniEnv.evaluate(source);
console.log(result); // 输出: 3
```

示例 2：嵌套组合（条件 + 副作用）

```javascript
const source2 = [
  'if',
  ['add', 1, 2],    // 条件: 3 (真)
  ['print', 'yes'], // then: 打印 "yes"
  ['print', 'no']   // else: 打印 "no"
];

MiniEnv.evaluate(source2);
// 输出: yes
// 返回: "yes"
```

示例 3：未定义的操作 → Unknown

```javascript
const source3 = [
  'multiply', 3, 4
];

const result3 = MiniEnv.evaluate(source3);
console.log(result3);
// 输出: { anchor: {}, op: 'multiply', args: [3, 4] }

// 检查是否是 Unknown
if (result3.anchor === Unknown) {
  console.log('这是一个 Unknown，当前环境无法解释它');
}
```

示例 4：原子操作也可以作为值被传递

```javascript
// 将操作名作为值传递
const source4 = [
  'add',
  ['add', 1, 2],   // 第一个参数是 3
  ['sub', 5, 3]    // 第二个参数是 2
];

console.log(MiniEnv.evaluate(source4)); // 输出: 5
```

## 概念对应表

| Origin 抽象 | 此示例中的对应 |
|---|---|
| **值** | 数字 `1`、`2`，字符串 `"yes"`，以及 `Unknown` 标记对象。所有值都可区分（对于原语使用值比较，对于对象使用引用比较；示例中统一使用 ===）。|
| **操作** | `add`、`sub`、`if`、`print`。它们是注册在 `ops` 表中的函数。执行时“发生作用”（计算、输出、分支选择）。 |
| **环境** | `MiniEnv` 对象本身。它持有原子操作注册表（`ops`）和解释规则（`evaluate`）。 |
| **组合** | 数组结构 `['add', 1, 2]`。它描述了“操作名”和“参数”之间的关系。数组本身不执行，直到被 `evaluate` 处理。 |
| **源代码** | `source`、`source2`、`source3` 等变量。它们是组合结构的载体。 |
| **原子（相对性）** | `add` 在 `MiniEnv` 中是原子操作。但它底层可能由 JS 引擎的多个微操作构成。`MiniEnv` 不关心这些，它只声明：“在我的边界内，`add` 是不可再分的”。 |
| **穿透** | 本例未启用穿透。`MiniEnv` 只使用自己 `ops` 表中的操作。如果要启用穿透，可以让 `evaluate` 在找不到操作时，尝试向底层环境（如 JS 全局对象）请求同名函数。 |
| **Unknown** | 当操作名不存在时，返回一个包含 `Unknown` 公共锚点的结构。这是一个明确的、可区分的标记，而不是静默返回 `undefined` 或抛出异常。决策者可以通过检查 `result.anchor === Unknown` 来决定后续行为。 |
| **环境构造** | 如果决策者希望扩展 `MiniEnv`，可以创建一个新对象，继承或合并 `MiniEnv.ops`，并添加自己的原子操作。新环境拥有 `MiniEnv` 的全部能力，同时具备自己的扩展。 |
| **结构保持** | 同一份 `source` 结构，如果被另一个具有相同操作名的环境解释，可能产生不同结果（例如 `add` 在另一个环境中被定义为字符串拼接）。结构本身不变，环境响应不同。 |


## 示例环境的局限

此示例有意保持极小，因此它**没有**包含以下特性：

- 类型系统或类型检查；
- 变量绑定或作用域（所有值都是立即求值的字面量）；
- 内存管理或垃圾回收的显式控制；
- 并发、异步或并行执行模型；
- 穿透的完整实现；
- 错误恢复机制（未知操作返回 `Unknown` 是一种策略，但不是唯一的策略）；
- 源代码的文本解析器（本例中“源代码”直接以数组形式给出，省略了解析步骤）。

这些缺失都不是缺陷，而是**设计选择**。如果一个真实环境需要这些特性，它们应当由该环境的实现者根据具体需求逐步“生长”出来，而不是一次性从核心中继承。这正是 Origin“能力生长”理念在具体实现层面的体现。


## 扩展练习

如果读者希望基于此示例进一步探索，以下是几个可能的扩展方向：

1. **添加变量绑定**：在环境中增加一个 `env` 对象，用于存储变量名到值的映射，并添加 `let` 和 `get` 操作。
2. **实现穿透**：修改 `evaluate`，在 `ops` 中找不到操作时，尝试调用 `globalThis[opName]`（或类似机制），让 JavaScript 原生函数可以作为其它环境的原子操作进入。
3. **支持自定义 Unknown 行为**：将 `Unknown` 的返回策略改为可配置的回调函数，让决策者可以自定义“未定义操作”时的行为（例如抛出异常、返回默认值、记录日志等）。
4. **提供文本解析器**：为数组结构编写一个简单的文本语法（例如 `"(add 1 2)"`），让结构可以从文本字符串中解析而来。

这些扩展都不是 Origin 核心的要求。它们的存在只说明一件事：**当一个环境被构造出来之后，能力可以从这个环境中继续生长。**
